# [RFC] Add FmaOp to the StableHLO specification

Status: Review<br/>
Initial version: 10/17/2026<br/>
Last updated: 10/19/2026<br/>
Discussion thread: [GitHub](https://github.com/openxla/stablehlo/pulls)

## Motivation

Fused multiply-add computes `a * b + c` with a single rounding step instead of
rounding `a * b` first and then rounding the sum. It is part of IEEE-754
(`fusedMultiplyAdd`), C99 (`fma`), and LLVM (`llvm.fma`).

Hardware support varies across chips. Most CPUs and GPUs have a single
instruction for fused multiply-add. Other chips, such as TPUs, do not have
native fused multiply-add for all floating-point types and run multiply and add
as two separate instructions unless single rounding is emulated in software.

Today, StableHLO only has separate `multiply` and `add` operations. Code that
needs exact single-rounded `a * b + c` for numerical accuracy cannot express it,
because `add(multiply(a, b), c)` rounds twice.

This RFC adds `fma` (`FmaOp`) for floating-point tensors, matching IEEE-754
`fusedMultiplyAdd` and LLVM's `llvm.fma`. It computes `a * b + c` with a single
IEEE-754 rounding step. If the target chip does not have a native FMA
instruction for the element type, the backend must emulate single rounding in
software.

## Proposed Specification Changes

See [`docs/spec.md`](../docs/spec.md) for the specification of
[`fma`](../docs/spec.md#fma).

### Emulation in Higher-Precision Floating-Point Types

Simply upcasting a narrow floating-point type (such as `bf16` or `f16`) to a
higher-precision type (such as `f32`), computing `fma` there, and rounding back
to the narrow type is not in general a valid implementation of `fma` because of
double rounding and intermediate underflow or overflow:

* **Upcasting and computing a single wider `fma` fails due to double rounding**:
  Rounding `a * b + c` to a wider type first and then to the target type can
  differ from single-rounded `fma` in the target type. Avoiding double rounding
  requires a wider type with extra exponent range (such as `f64` for `bf16`, or
  `f32` for `f16`) and round-to-odd on the wider addition before the final
  rounding. In `bf16`, for `a = 1.5` (`0x3fc0`), `b = 1 + 2^-7 = 1.0078125`
  (`0x3f81`), and `c = -2^-24` (`0xa780`), the exact value
  `a * b + c = 1.5 + 2^-7 + 2^-8 - 2^-24` rounds in single-rounded `bf16` `fma`
  to `1.5 + 2^-7 = 1.5078125` (`0x3fc1`), whereas `f32` `fma` first rounds to
  the `bf16` midpoint `1.5 + 2^-7 + 2^-8 = 1.51171875` (`0x3fc18000`) and then
  rounds to `bf16` as `1.5 + 2^-6 = 1.515625` (`0x3fc2`).
* **Same-exponent-range wider types can overflow or underflow intermediates**:
  Because `bf16` and `f32` share the same minimum normal exponent (`-126`), a
  product of two `bf16` normals can be an `f32` subnormal that still rounds up
  to the smallest `bf16` normal `2^-126`. For example, for
  `a = 129 * 2^-70 = (1 + 2^-7) * 2^-63` (`0x2001`),
  `b = 127 * 2^-70 = (1 - 2^-7) * 2^-63` (`0x1fff`), and `c = 0.0` (`0x0000`),
  single-rounded `bf16` `fma` rounds the exact product
  `(1 - 2^-14) * 2^-126` up to `2^-126` (`1.17549435e-38`, `0x0080`, even when
  `bf16` flushes subnormals to zero), whereas an `f32` multiply that flushes
  subnormals to zero flushes the intermediate product to `0.0` and returns `0.0`
  (`0x0000`).

## Compatibility

* **VHLO**: StableHLO `1.24.0` adds `VHLO_FmaOpV1` (`fma_v1`).
* **Older versions**: `fma(a, b, c)` cannot be downgraded to StableHLO versions
  older than `1.24.0`, because `add(multiply(a, b), c)` rounds twice and would
  break its single-rounding guarantee.

## Alternatives Considered

### Adding a separate unfused-tolerant `fmuladd` operation

We considered also adding an `fmuladd` operation (analogous to LLVM's
`llvm.fmuladd`) that permits the backend to compute either single-rounded
`fusedMultiplyAdd(a, b, c)` or two-rounded `add(multiply(a, b), c)`, preferring
a hardware FMA instruction where available. We decided against adding `fmuladd`
to StableHLO for two reasons:

* **Frontend target-aware lowering is sufficient**: Frontends such as JAX
  already know whether the target supports native FMA for a given element type.
  They can lower an unfused-tolerant `fmuladd` primitive directly to
  `stablehlo.fma` on targets with hardware FMA (such as CPU and GPU) and to
  `stablehlo.add(stablehlo.multiply(a, b), c)` on targets without native FMA
  (such as TPU).
* **Naive wider-type emulation pitfalls still apply**: Even for an
  unfused-tolerant `fmuladd`, simply upcasting `bf16` to `f32` and computing a
  single `f32` `fma` can double-round to a value matching neither single-rounded
  `fma` nor two-rounded `add(multiply(a, b), c)` in `bf16` (for example,
  `a = 1 + 2^-7`, `b = 1 - 2^-7`, `c = -1.0` gives `0.0` with two `bf16`
  roundings, whereas `f32` `fma` rounded to `bf16` gives `-2^-14`). Similarly,
  two-step evaluation of `bf16` in `f32` fails when `f32` flushes subnormals to
  zero, because an `f32` subnormal product that should round up to the smallest
  `bf16` normal `2^-126` is flushed to `0.0`.
